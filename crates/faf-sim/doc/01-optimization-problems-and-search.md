# 1. Optimization Problems and Search

Before we add machine learning, let's look at the problem the way a classical
optimizer sees it. This chapter explains why FAF build orders are hard and why
a simple search already needs clever tricks.

## What is an optimization problem?

An optimization problem has three parts:

1. **Variables:** the things we can choose.
2. **Constraints:** the rules we must respect.
3. **Objective:** the number we want to minimize or maximize.

For a FAF build order:

- **Variables:** which unit to build next, when to start it, and which builders
  to assign.
- **Constraints:** builders can only do one thing at a time; you need the right
  technology to build a unit; the economy must pay for construction.
- **Objective:** minimize the in-game time when the last goal unit finishes.

The secondary objective from `model.md` — mass income per mass invested in
economy — is a refinement: among plans that finish at the same time, prefer the
one that spent less mass on economy.

## The search space is enormous

Suppose at each moment you have roughly 10 reasonable things to build and a
handful of builder choices. Over a 10-minute build order there might be 50
building decisions. Even a conservative branching factor gives an unimaginably
large number of possible plans.

Humans solve this by learning patterns: "open with 2 mex, 2 pgens, 1 factory,
2 engineers, then tech." A program can either:

1. **Search:** explore many possible plans and keep the best ones.
2. **Learn:** remember which decisions tend to lead to good outcomes.

The current `faf-sim` planner uses search: beam search guided by a heuristic.

## Beam search in plain language

Beam search is like breadth-first search, but instead of keeping *every*
possible state, it keeps only the best `K` states at each layer. `K` is the
"beam width."

In `faf-sim`:

- A **state** is a `sim::GraphState` at a point in time.
- A **layer** is one search step.
- The **score** estimates how much longer the plan will take to reach the goal.

Beam search is fast and often finds good plans, but it has a weakness: the
heuristic that scores states is hand-written. If the heuristic undervalues an
unusual but strong choice, beam search will discard it before discovering that
it pays off later.

## The limit of hand-written heuristics

A heuristic is a shortcut. It says, "this state looks promising because it has
a lot of build power" or "this state looks bad because it is energy stalled."
Hand-written heuristics encode human intuition.

The problem is that human intuition can miss non-obvious strategies. For
example, a slightly slower early economy might enable a much faster tech path
later. A learned value function can, in principle, spot patterns that a human
did not think to encode.

## When does machine learning enter?

Machine learning is not magic. It is a way to build a scoring function — or an
entire decision policy — from data instead of from human rules.

For FAF, the data is generated by the simulator itself. We can run thousands or
millions of build orders and remember which states led to fast completions.
Over time, a learned model can:

- Estimate the remaining time from any state (a **value function**).
- Suggest the best next action (a **policy**).
- Or both.

The next chapters introduce the machine-learning concepts we need. We will
start with the broad idea of learning from data, then narrow in on
reinforcement learning, the branch of ML best suited to sequential decision
problems like build orders.
